# Backlog

## 主句 + 括号语境输入

用户输入可以支持两层结构：

```text
相比于生活的困境，我一直更害怕的是怯弱的自己。
（只有自己最懂自己，越害怕越回避）
```

设计原则：

- 括号外是 `main_text`，用于字幕、旁白、视频核心表达。
- 括号内是 `context_note`，用于情绪理解、语义扩充、分镜、音乐和视觉方向。
- 默认 `context_note` 不直接进入字幕和旁白，避免解释感破坏留白。
- 后续可增加选项：仅用于理解、作为结尾字幕、作为旁白补充、完全忽略。

建议新增：

```text
services/input_parser_service.py
```

结构：

```json
{
  "raw_text": "...",
  "main_text": "...",
  "context_note": "...",
  "has_context_note": true,
  "context_usage": "guide_only"
}
```

链路使用：

- `emotion_service`: `main_text + context_note`
- `semantic_service`: `main_text + context_note`
- `subtitle_service`: `main_text` only
- `storyboard_service`: `main_text + context_note + subtitles`
- `audio_plan`: subtitles only
- `image_prompt`: storyboard + context_note

## Key Visual + I2I 连续性实验

当前先采用文字连续性控制：

```text
subject / location / recurring objects / lighting / palette
```

后续可实验更强一致性：

```text
1. 先用 T2I 生成 key_visual.png
2. 后续镜头使用 image-to-image 参考 key_visual
3. 控制不同景别、角度和动作
```

注意风险：

- 首图不好会带偏整条视频。
- I2I 可能导致镜头过于相似。
- 情绪 MV 不一定需要同一张脸完全一致，更需要同一气质、空间和光线。

## 后期优化优先项

### 1. 音色一致性

当前旁白按字幕分段生成，虽然默认主声线、括号声线和提问声线可以使用同一个 `voice_id`，但不同分段的 `speed`、`pitch`、`volume`、`emotion` 以及旧音频缓存复用，仍可能造成“像多个人说话”的听感。

后期优化方向：

- 固定整条视频的基础 `voice_id`、`pitch`、`emotion`，把括号和提问的差异收敛到轻微语速、音量和停顿。
- 优先实验“整段一次 TTS + pause 标签控制停顿”，减少分段生成带来的音色漂移。
- 如果继续分段生成，生成前应清理或按 plan hash 命名旧的 `narration_*.mp3`，避免旧配置音频混入。
- 报告中记录每段实际使用的 `voice_id`、`speed`、`pitch`、`emotion`，方便 UI 展示和排查。

### 2. 人物一致性与自定义角色图

当前人物一致性主要依赖文字 prompt，例如 `same ordinary adult throughout the video`，但每张图仍是独立生成，无法真正锁定同一个人。

后期优化方向：

- 轻量版：支持上传 1 张主角参考图，提取人物设定描述，并注入所有镜头 prompt。
- 稳定版：支持上传三视图或多参考图，例如正面、侧面、背影/半身，适合情绪 MV 中的背影、侧脸、低头、远景镜头。
- 高阶版：建立角色资产包，包含参考图、年龄、发型、服装、气质、禁用变化项。
- 图像生成链路优先实验 `key visual + image-to-image/reference image`，而不是只依赖文字连续性。

### 3. 括号意境分层

括号内容不一定只是解释，它可能是主句的反转、点醒、补刀或价值判断。主句和括号应分开分析，再合成一条完整的情绪运动。

示例：

```text
我的脑子，笔记本，以及电脑中记了太多的遗留待办，却一直都只是遗留。
（机会青睐的，永远是那些已经行动的人儿）
```

更合理的结构：

- `main_theme`: 遗留待办、堆积、停滞、未完成。
- `parenthetical_theme`: 机会、行动、提醒、反转。
- `relationship`: 括号是对主句的点醒，不是普通补充说明。
- `visual_transition`: 前段以堆积和停滞为主，后段逐渐转向手指靠近执行按钮、屏幕光变亮。
- `style_rule`: 视觉风格保持统一，但情绪运动允许从停滞转向行动。

### 4. 提问环节

当前可以通过用户输入问号触发 `question` 角色，但产品上还没有独立的提问环节配置。

后期优化方向：

- UI 增加“提问环节”选项：不加入、自动生成、用户手动填写。
- 自动生成时，根据主句生成一句自我追问，例如“我到底是在整理生活，还是在推迟开始？”
- 提问层在表达计划中使用 `question` role，旁白保持同一音色，只在语气和停顿上轻微区分。
- 分镜上提问可以对应静止凝视、手停在按钮前、窗口反光等“悬置镜头”。

### 5. FFmpeg 性能优化

当前最后合成 MP4 较慢，后期应把更多拼接、缩放、字幕叠加、音频混合工作下沉到 FFmpeg，减少 Python/MoviePy 逐帧处理压力。

后期优化方向：

- 优先用 FFmpeg filtergraph 完成图片转视频、转场、缩放裁切、字幕叠加和音频混合。
- 复用已生成图片和音频，只重跑最终合成时避免重新进入上游步骤。
- 配置化 `preset`、`threads`、`crf`、`fps`、`audio_codec`，在质量和速度之间提供可调档位。
- 输出 `video_compose_timings.json`，记录图片准备、字幕、音频、编码等阶段耗时，方便 UI 显示瓶颈。

## 优化罗盘与执行规划

目标：把项目从“能生成情绪 MV 的脚本工具”，逐步优化成“可持续使用、可排查、可复用、可控制风格的创作产品”。

### P0：先让生成过程可控、可恢复

#### 1. 生成过程可视化（已完成基础版）

目标：
- UI 中展示完整生成链路：情绪分析、表达计划、意境分析、分镜、图片、旁白、BGM、视频合成、报告。
- 每一步显示 `pending / running / success / failed`。
- 显示每一步耗时和失败原因。

完成标准：
- 用户不用打开文件夹，也能知道卡在哪一步。
- 失败时 UI 能展示具体错误，而不是只看到没有视频。
- `run_events.jsonl` 中的信息可以被 UI 直接消费。

当前状态：
- UI 已展示生成步骤、状态、耗时和失败信息。
- 图片生成和视频合成支持进度回传。
- 后续可继续增加“重试当前失败步骤”的操作按钮。

#### 2. 报告 UI 化（已完成基础版）

目标：
- 把 `run_report.json` 从纯 JSON 变成用户能读懂的报告面板。
- 重点展示：最终视频、运行目录、总耗时、失败项、fallback 情况、BGM 状态、图片状态、视频合成耗时。

完成标准：
- 用户只看报告页，就能判断这次生成是否成功、哪里质量可能有问题。
- 报告中可以看到 `music_generation_failed`、`used_music_fallback`、`fallback_images` 等关键信息。

当前状态：
- UI 已展示报告摘要、最终视频、运行目录、BGM/fallback 状态、关键 warning 和性能耗时。
- `run_report.json` 与 `run_report.md` 继续作为完整报告。
- 后续可继续增加报告中的“单步重试入口”。

#### 3. 断点续跑与失败恢复

目标：
- 支持按步骤重跑：只重跑 BGM、只重跑旁白、只重跑图片、只重跑最终合成。
- 复用已有图片、音频、分镜和报告。

完成标准：
- 图片已生成时，重合成不会重新请求图片 API。
- BGM 失败后，可以只补 BGM 并重新合成。
- 最终合成失败后，可以只重跑视频合成。

当前状态：
- 已有 `scripts/recompose_run_video.py`，可以复用图片、旁白、分镜和音频计划重拼视频。
- BGM 生成会优先复用已有 `bgm.mp3`，不存在时才重新请求。
- 后续需要 UI 化单步恢复。
